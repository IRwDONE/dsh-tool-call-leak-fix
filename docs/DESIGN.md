# 结构化输出退化：工具调用参数边界丢失（分析与修复方案）

> 本文写作时**刻意分块写入**、且尽量不连续书写字面闭合标签——这本身就是被分析的故障的现场对策。
> 记法约定：文中「闭合标签」指形如 `</` 开头的标签（HTML/CSS/XML/调用标记都算）。

## 0. 结论摘要

- **定性**：不是 DSH 的 bug，也不是某个项目的 bug，而是**模型侧的结构化输出退化**，具体子类为
  **工具调用参数边界丢失（tool-call argument boundary loss）**。
- **最危险之处**：静默失败。调用没执行、也没有报错，从流程上看像是"做完了"。
- **为什么会"一次坏、一直坏"**：损坏的输出一旦落进对话上下文，模型会把它当作已成立的格式继续模仿；
  compact 只压缩体积、不消除这个样本，所以过一阵子必然复发。
- **可修复性**：DSH 侧存在**契约级可用**的插件接缝，可以把"故障 → 发现 → 纠正"的闭环从
  **人（用户）来发现** 改成 **harness 自动发现并当场自愈**。见 §5 与 `docs/CONTRACTS.md`。
- **不能修复的**：插件改不了模型本身。它只能缩短故障窗口、把静默失败变成显式失败、并在同一 turn 内重试。

## 0.1 契约修订（2026-10-28，据 `docs/CONTRACTS.md` 实测）

实测**推翻/修正**了初稿的若干假设，以实现文档为准：

1. **不存在文本协议解析器**。DSH 全树没有形如调用信封（`<` + `invoke name=` …）的文本协议解析器；
   本机路由 provider=`nvidia` / model=`deepseek-ai/deepseek-v4.1-flash`，走 pi-ai 的
   **`openai-completions` 原生 tool_calls**（流式 JSON 分片）。
   ⇒ 模型把信封当正文吐出时，**没有任何解析器会把它变成真实调用**：它只成为 text 块 →
   agent-loop 见 `toolCalls.length === 0` → 直接 `{kind:'completed'}`（不执行、不报错、turn 正常关闭）。
   ⇒ **`tools/pre-execute` 在该场景下根本不会被触达**；检测只能挂 `session/event`(`assistant/message`)。
2. **新增变体 V4（同族的第二种静默失败）**：pi-ai 的 `parseStreamingJson()` 对非法 JSON
   **永不抛错**，依次 `repairJson` → `partial-json` → 最终 `return {}`。
   即"参数被静默清空成空对象"，工具会带着空参数执行。**这一种是可以被 `tools/pre-execute` 拦住的**
   （与上面的正文泄漏互为补充的两条路径）。
3. **M5 挂点修正**：`LlmCallConfig` 不含 messages，`agent/request` 无法改写历史；带 messages 的是
   `GenerateOptions`，即 **`llm/stream` waterfall 的 `options`** —— 那才是"隔离损坏文本"的唯一确证挂点。
4. **M4 机制确证**：`agent/turn-stopping`（serial）之后 agent-loop 仍有一次 `nextStep.length === 0` 判空；
   此时 `agent.inject(...)` 注入 next-step 消息即可让 turn 不关闭、**同一 turn 内**继续 → 自愈成立。
5. 桌面版 asar 内 `.d.ts` **已被剥离**（18188 个文件里 0 个）；精确签名改用各包
   `lib/typert.host.js` 里内嵌的 `"declaration"` 字符串与构建产物源码取证。

## 1. 定性

### 1.1 这属于哪一类

| 层 | 是不是 | 说明 |
| --- | --- | --- |
| DSH（harness） | **不是** bug | 它在多数路径上只是**正确地把损坏输出当作正文**处理；问题不在它的解析逻辑 |
| 具体项目 | **不是** bug | 与项目内容无关，任何长 payload 都可能触发 |
| 模型侧结构化输出 | **是** | 生成阶段丢失了参数边界（结束序列重复、开场序列缺失、内容外泄） |

一句话：**这是生成侧的序列边界坍缩**，不是接收侧的解析缺陷。
把它当作"DSH 的 bug"去修会修错地方；把它当作"模型偶尔手滑"会低估它——它是**有触发条件的、可复发的、会自锁的**。

### 1.2 三个观测变体（签名表）

| 变体 | 观测形态 | 解析结果 | 危害 |
| --- | --- | --- | --- |
| **V1 结束序列增殖** | 参数末尾出现重复的结束序列（外层收尾标记连续出现数次） | 结构被判坏 / 多余内容归属不明 | 调用不执行；**且看起来像已执行** |
| **V2 开场序列缺失** | 只有 `<parameter name="...">` 而没有外层 `<invoke name="...">` | 整段退化为普通正文 | 静默 no-op（最隐蔽） |
| **V3 正文泄漏** | 参数内容出现在 assistant 正文里，工具一张卡都没出现 | 完全没被识别为调用 | 静默 no-op + 上下文污染 |

三个变体的共同点：**都不报错**。这就是它比"报错"危险得多的原因。

### 1.3 真实证据

**证据 A（用户提供）**：一次真实故障中，单个工具调用的参数体内含大段闭合标签。Abridged：

```
<parameter name="code">const fs = await import("node:fs/promises"); ... </parameter>
<parameter name="description">Read ui.html size and profile job output</parameter>
</invoke>        ← 此处起，外层结束序列重复增殖（原样共 4 组）
```

**证据 B（本次会话内自动复现，2026-10-28）**：本文件**第一次写入时 payload 尾部静默丢失**——
写工具返回成功，回读却发现结束代码围栏与后半段消失，且**没有任何报错**。
这与 V1/V3 同构（长 payload + 闭合标签邻近 → 尾部丢失），也是"落盘后必须回读"的现场证明。

## 2. 触发条件（相关性）

不是随机手滑，而是**可预测的条件组合**：

| 条件 | 作用 | 强度 |
| --- | --- | --- |
| **payload 长度**（经验阈值：> ~100 行 或 > ~8–10k 字符） | 主因之一；越长越易丢尾 | 强 |
| **payload 内容含大量以 `</` 开头的闭合标签**（HTML/CSS/XML/JSX/调用标记） | **关键因子**：与调用语法本身同形，最易与边界混淆 | **最强** |
| **连续多次同类长写入** | 疲劳累积；上一份长 payload 仍在上下文里 | 中 |
| **上下文里已存在损坏样本** | 自模仿：模型把损坏格式当既定格式 | **强（自锁）** |
| 模板字符串 / `String.raw` / 多层转义 | 转义层叠加，边界更脆 | 中 |

**关键推论**：危险 ∝（长度 × 闭合标签密度），并被"上下文里已有损坏样本"放大。
所以**只靠降低单次长度不够**——必须同时打断"损坏样本继续留在上下文里"的自锁。

## 3. 危害

1. **静默 no-op（最危险）**：调用未执行、无报错、界面无异常 → 后续步骤建立在"已做"的假设上，
   错误被放大成事实。这正是"看起来成功"的失败。
2. **对话级自锁**：损坏样本进入上下文 → 复发率上升 → 输出质量整体下滑。
3. **突兀中止**：用户观察到"整个对话就会持续发生该问题，然后没有良好的输出也会直接中止"。
4. **compact 无效**：压缩只减体积，不会删除或标记这个坏样本，所以"过一阵子还会再出现"。
5. **影响面**：所有长文本写入类工具（文件写入、`run_code` 代码参数、批量编辑）。

## 4. 现有缓解（已采用）与其天花板

已采用（模型侧自律）：

1. 单块 ≤ 100 行，超出就分块（首块 `write`，其余追加）；
2. 落盘后**回读校验**（行数 + 关键标记）；
3. 避免 `String.raw` / 避免在参数里写超长模板字符串；
4. 闭合标签用拼接构造，不写完整字面序列；
5. 单次调用末尾只允许一个结束序列。

**天花板**：这五条全部依赖"模型在退化时仍然守规矩"。
而退化本身就是**自律失效**——所以它们在触发点附近恰恰最不可靠。
证据 B（§1.3）就是活证：明知规则、仍在同一次写入里丢了尾巴。
⇒ 需要**外部强制**：harness 侧检测 + 纠正。这正是插件要做的事。

## 5. 插件方案

### 5.1 设计原则

- **只做能被证明的事**：每条机制都绑定一个已核实的契约接缝，不做猜测性 hook。
- **三层强度，递进**：预防（prompt）→ 拒绝/标记（dispatch 前）→ 自愈（同 turn 重试）。
- **保留他人贡献**：waterfall listener 不接管决策时一律 `next()`；只加不改。
- **宁可显式失败，不要静默失败**：把 no-op 变成"响亮、可操作"的结果。

### 5.2 机制与接缝对照表（已核实）

| # | 机制 | 接缝（契约） | 拦住哪个变体 |
| --- | --- | --- | --- |
| M1 | 注入预防性纪律块 | `ctx.systemPrompt.section({name, order, text})` | 降低全部变体发生率 |
| M2 | 分发前扫描参数边界 | `tools/pre-execute` → `{kind:'deny', reason}` / `ctx.tools.guard()` | V1（结构尚可解析但已损坏） |
| M3 | 结果后纠偏 | `tools/post-execute` → `PostToolDecision`，可带 `additionalContexts`（或 `{kind:'block', feedback}`） | 写入类工具的"假成功/空转" |
| M4 | **静默 no-op 自愈** | `agent/turn-stopping`（turn 即将关闭）或 `session/event`/`agent/pre-step` | **V2 / V3**（最关键） |
| M5 | 上下文隔离（可选、需契约确认） | `agent/request`（改写 `LlmCallConfig`） | 打断"损坏样本自锁" |
| M6 | 硬性小块写入工具 | `ctx.tools.register()` + 服务端行数上限 | 从源头限制单次 payload |

### 5.3 M4 为什么是关键

V2/V3 的本质是：**模型吐出的调用标记根本没被识别成调用，turn 正常结束**。
此时没有任何工具被调用，所以 M2 永远不会被触达——只有"turn 即将结束"这个观察点能发现它。
发现后在同一条 turn 内注入一条纠正指令（steering），让模型立刻按小块重发，
就把"用户发现 → 用户质问 → 手动重来"换成"harness 自动发现 → 当场重试"。

### 5.4 边界（做不到什么）

- **改不了模型**：插件只能缩短故障窗口，不能消除退化本身。
- **M5 依赖契约**：若 `LlmCallConfig` 不含 messages（或不可改写），"上下文隔离"降级为
  "在下一步注入一条校正说明"，效果弱一些。以 `docs/CONTRACTS.md` 的实测结论为准。
- **原生 function-calling 路径**：若参数由 provider 原生 JSON 组装，且 JSON 解析失败被上层吞掉，
  则插件在 dispatch 之前**无法**看到损坏（只能靠 M4 观察 assistant 文本）。
- **有自愈就会有额外调用**：M4 触发会多一次模型请求，这是成本，用 `Config` 里的开关与次数上限约束。

### 5.5 提示词

两份现成文本见 **`docs/PROMPTS.md`**：

- **(A) 预防型**：注入 system prompt 的规则块（M1 直接使用）。
- **(B) 纠正型**：检测到损坏时注入的指令（M4 直接使用）。

两者都刻意"短"：超长提示词会稀释注意力，与要解决的问题背道而驰。

## 6. 可测量的成功判据

| 判据 | 目标 | 如何测 |
| --- | --- | --- |
| 检测召回 | 3/3 变体样本被识别 | `tests/` 回放用例 |
| 误报 | 对正常代码/HTML/长文本 0 误报 | 反例样本集 |
| 静默失败归零 | 损坏时 turn 不静默结束，至少产出一次纠正注入 | 事件断言（turn-stopping 处的注入计数） |
| 额外开销 | 每次纠偏增加 ≤ 1 次模型请求；有次数上限 | 注入计数 + Config 上限 |
| 幂等/安全 | 不破坏正常调用；deny 一律带可操作 reason | 单元测试 + 现场抽查 |

## 7. 测试台

`tests/` 回放三个真实变体（V1 结束序列增殖 / V2 开场缺失 / V3 正文泄漏）+
一组反例（正常 HTML、正常长 JS、正常 Markdown 表格），
以**纯函数级**方式测试检测器（不依赖 DSH 运行时），
再用一次真实会话做端到端验收。

## 8. 判定用语（避免混淆）

- ✅ 可以说：**这是一个有触发条件、可复现、可检测、可自愈的模型侧结构化输出退化**。
- ❌ 不要说：这是 DSH 的 bug / 这是随机手滑 / 加大 prompt 就能解决。
